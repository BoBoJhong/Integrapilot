# 整合評估工具演化建議書（Roadmap v1）

## 1) 文件目的

這份文件定義本工具從「可用」走向「好用、可擴充、可營運」的演化路線，給產品、工程與使用者共用同一張優先級地圖。

適用範圍：
- Web 介面（評估、報告、對話）
- FastAPI 後端（API、任務執行、儲存）
- Docker / 部署與維運

---

## 2) 現況（2026 Q1）

已完成基礎能力：
- 兩專案整合評估、報告存檔與預覽
- Agent 對話、ZIP/Git 匯入、Word 匯出
- 前端 TypeScript 化、Element Plus 按需引入
- 後端模組化、健康檢查、基礎速率限制
- 基本 pytest 煙霧測試

現況主要限制：
- 評估與對話仍是同步長請求，使用者等待體感重
- 報告生命週期管理偏弱（缺比較、缺標籤、缺檢索）
- 可觀測與營運數據不足（成本/成功率/延遲追蹤不完整）

---

## 3) 產品北極星與成功指標

### 北極星目標
「讓團隊在 10 分鐘內，從兩個專案快速得到可執行整合方案，並能持續追蹤決策演進。」

### KPI（建議）
- 首次成功評估率 >= 90%
- 評估任務中位完成時間 <= 120 秒
- 對話回覆成功率 >= 98%
- 報告二次利用率（同報告至少 2 次互動）>= 60%
- 匯出（md/docx）成功率 >= 99%

---

## 4) 演化階段與優先順序

## Phase A：穩定性與可觀測（1-2 週）
目標：讓系統在真實使用下「可預期、可除錯」。

建議項目：
- 導入 request id 與結構化日誌（API 全路徑）
- 錯誤碼分層（使用者錯誤 / 系統錯誤 / 外部依賴）
- 增補測試：`/api/assess`、`/api/chat`、上傳與 clone 失敗情境
- 增加執行統計：成功率、耗時、錯誤原因分布

完成定義（DoD）：
- 可在 5 分鐘內定位 80% 常見錯誤原因
- 測試覆蓋關鍵流程且 CI 必跑

## Phase B：非同步任務化（2-3 週）
目標：把長任務從「卡住頁面」改成「可追蹤作業」。

建議項目：
- 新增 Job 模型（`queued/running/succeeded/failed/cancelled`）
- `POST /api/assess` 改為建立任務，回傳 `job_id`
- 新增 `GET /api/jobs/{id}` 輪詢進度（必要時加 SSE）
- UI 顯示進度條、預估時間、可取消/重試

完成定義（DoD）：
- 使用者可離開頁面再回來，仍能接續查看進度/結果
- 後端重啟後任務狀態不遺失（最少持久化 metadata）

## Phase C：報告資產化（2-4 週）
目標：報告從一次性輸出，升級為可搜尋、可比較的知識資產。

建議項目：
- 報告 metadata（專案、版本、日期、標籤、模型）
- 報告清單搜尋與篩選（關鍵字、時間、專案）
- 差異比較（兩份報告重點差異）
- 可固定結論區塊（風險、里程碑、待補資訊）

完成定義（DoD）：
- 使用者可在 30 秒內找到任一歷史報告
- 可一鍵比較兩次評估差異

## Phase D：對話可信度與落地輸出（2-3 週）
目標：讓 Agent 回覆可追溯、可執行，而不只是「看起來合理」。

建議項目：
- 回覆附來源段落引用（對應報告章節）
- 一鍵轉「行動清單」（Owner / Due date / 風險）
- 匯出任務格式（Markdown checklist / CSV）
- 對話模板（安全審查、整合計畫、風險追蹤）

完成定義（DoD）：
- 主要回答可附來源依據
- 使用者可直接把對話結果帶進專案管理工具

## Phase E：團隊化與治理（4 週+）
目標：支持多人協作、治理與後續商業化可能。

建議項目：
- 專案與角色權限（viewer/editor/admin）
- Agent 與規則模板共享
- 成本治理（模型使用量、token、估算費用）
- 基礎審計（誰在何時對哪份報告做了何操作）

---

## 5) 近期建議實作組合（MVP+）

若只能先做三件，建議優先：
1. 非同步任務化（Phase B 核心）
2. 報告 metadata + 搜尋（Phase C 核心）
3. 對話來源引用 + 行動清單輸出（Phase D 核心）

理由：
- 同時提升「體驗、可信度、留存」
- 對現有架構改動相對可控
- 可在 4-6 週看到明顯產品價值

---

## 6) 風險與緩解

- 風險：LLM 回覆品質波動  
  緩解：提示詞模板化、固定輸出框架、引用檢核

- 風險：長任務造成資源壓力  
  緩解：佇列 + concurrency 上限 + 任務逾時策略

- 風險：資料成長造成查詢變慢  
  緩解：報告 metadata 結構化與索引、分層存檔

---

## 7) 建議里程碑（可調整）

- M1（第 2 週）：完成 Phase A
- M2（第 5 週）：完成 Phase B（可穩定輪詢進度）
- M3（第 8 週）：完成 Phase C 核心（搜尋 + 比較）
- M4（第 10 週）：完成 Phase D 核心（引用 + 行動清單）

---

## 8) 立即可開工的工作拆分（下一 Sprint）

- 後端
  - 定義 job schema 與儲存格式
  - 實作 `/api/jobs` 相關端點
  - 評估流程改為背景執行器
- 前端
  - 新增 Job 狀態 UI 與輪詢 composable
  - 報告列表搜尋/篩選列
  - 對話卡片加入「來源引用」區塊
- 測試
  - job lifecycle 測試
  - 報告篩選與差異功能 smoke test

---

## 9) 結語

這份路線圖的重點，不是加更多功能，而是先把「耗時任務可追蹤、結果可回溯、輸出可執行」做扎實。  
只要 Phase B + C + D 核心落地，這個工具就會從 demo 等級進化為團隊可日常使用的產品。
