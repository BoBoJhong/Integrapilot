# 整合評估報告：專案 A 與專案 B

## 1. 執行摘要

經評估，專案 A 與專案 B 在技術棧上存在高度共通性（後端 Python/FastAPI、前端現代 JavaScript 框架），整合具備可行性。然而，兩專案在**多租戶架構的實現方式**和**認證機制**上存在根本性差異，這是整合過程中最大的挑戰。

**一句話結論：** 整合可行，但需透過 API 閘道作為核心轉接層，以橋接多租戶模型與認證機制的核心差異，實現最小風險與成本的漸進式整合。

## 2. 對齊點 (Alignment Points)

兩專案在以下方面具有高度一致性或可重用性，為整合提供了良好的基礎：

*   **後端程式語言與框架**: 兩專案後端均採用 **Python**，並以 **FastAPI** 作為推薦或主要的 Web 框架。這使得後端邏輯的理解、維護和協作成本較低。
*   **前端建置工具**: 兩專案前端都使用 **Vite** 進行開發與建置，方便環境配置和流程統一。
*   **API 風格**: 兩專案均暴露 **RESTful HTTP/HTTPS API**，且 FastAPI 自動生成 OpenAPI/Swagger UI 文件，有利於 API 介面的探索與對接。
*   **AI/LLM 整合**: 兩專案都深度整合了大型語言模型 (LLM)，均支援 **OpenAI GPT-4** 和 **Google Generative AI**。雖然整合庫不同 (LangChain vs. 直接 SDK)，但底層服務一致。
*   **密碼雜湊**: 兩專案均使用 **`bcrypt`** 進行密碼雜湊，確保了密碼儲存的安全性一致性。
*   **測試框架**: 兩專案後端均使用 **`pytest`** 進行測試，有利於測試流程和工具的統一。
*   **開發輔助工具與工作流**: 兩專案都廣泛使用 AI 輔助開發工具 (如 Cursor AI, Claude Agents) 和文件驅動開發模式 (`.agent/`, `docs/`)，有助於未來開發規範和知識共享。

## 3. 落差與摩擦點 (Gaps & Friction Points)

以下是兩專案在技術棧、架構或部署方面的主要差異，可能導致整合摩擦：

*   **多租戶架構模型 (核心差異)**
    *   **專案 A**: 採用**物理隔離**，每個租戶使用**獨立的資料庫**。
    *   **專案 B**: 採用**邏輯隔離**，在單一 PostgreSQL 資料庫中透過 `tenant_id` 欄位區分不同租戶的數據。
    *   **摩擦**: 這是最根本的差異，直接影響使用者、租戶等核心數據的共享和管理。無法直接統一資料庫層。
*   **認證與授權機制**
    *   **專案 A**: 主要使用 **Session-based 認證**，支援本地帳密與 SSO，Session 管理基於 `itsdangerous`。
    *   **專案 B**: 主要使用 **JWT (JSON Web Token) 認證**，基於 `python-jose`，為無狀態認證。
    *   **摩擦**: 兩種認證機制不兼容，無法直接共享使用者登入狀態。
*   **資料庫系統與存取方式**
    *   **專案 A**: 使用 **MySQL**，透過 `pymysql` **直接執行 SQL 語句**。
    *   **專案 B**: 使用 **PostgreSQL (含 `pgvector` 擴展)**，透過 **SQLAlchemy ORM (異步)** 進行資料庫操作。
    *   **摩擦**: 不同的資料庫系統、資料庫擴展 (B 的 `pgvector` 用於 RAG)、以及底層存取方式 (直接 SQL vs. ORM) 使得資料層無法直接共享或同步。
*   **部署與容器化程度**
    *   **專案 A**: 部署方式未明確強調容器化，主要為 `pip` 依賴安裝與 Uvicorn/Gunicorn 運行。
    *   **專案 B**: **高度容器化 (Docker/Docker Compose)**，包含多階段建置 Dockerfile、自動化 Alembic 資料庫遷移。
    *   **摩擦**: 專案 B 的部署流程更為現代和自動化。專案 A 需要進行容器化改造才能與 B 保持一致的部署和管理方式。
*   **前端框架**
    *   **專案 A**: Vue.js
    *   **專案 B**: React
    *   **摩擦**: 雖然都使用 Vite，但底層框架不同，導致 UI 組件無法直接重用，共同開發成本較高。
*   **LLM 整合庫**
    *   **專案 A**: `langchain`
    *   **專案 B**: 直接使用 `openai` 和 `google-generativeai` SDK
    *   **摩擦**: 雖然都連接相同的 LLM 服務，但抽象層不同。如果未來需要統一 LLM 呼叫的編排邏輯，則需選定一個標準或再包裝一層。
*   **Python 版本與依賴管理**
    *   **專案 A**: 未明確指定 Python 版本，但有 Flask 和 FastAPI 兩種運行模式，依賴文件有 `requirements.txt` 和 `requirements_fastapi.txt`。
    *   **專案 B**: 明確指定 Python 3.12，並有詳細的 `requirements.txt`。
    *   **摩擦**: 需確保兩專案的 Python 環境兼容，並仔細處理共享依賴庫的版本衝突。

## 4. 整合選項與取捨

考慮到上述對齊點與摩擦點，以下提出兩種主要整合選項：

### 選項一 (推薦): API 閘道 (API Gateway) 模式

*   **描述**: 在兩專案的前端與後端之間部署一個 API Gateway。此 Gateway 將作為所有外部請求的單一入口點，負責智能路由、統一認證、以及關鍵的**租戶識別轉換**。
*   **實施方式**:
    *   選擇一個 API Gateway 解決方案 (例如：Kong, Nginx + Lua, 或基於 FastAPI 自建輕量級 Gateway)。
    *   Gateway 負責接收來自前端的請求，根據 URL 路徑或特定的 Header 判斷應轉發到專案 A 或專案 B。
    *   在 Gateway 層實現統一的認證處理邏輯：
        *   將專案 A 的 Session 轉換為專案 B 可接受的 JWT，或反之。
        *   或者，引入一個外部的身份提供者 (IdP)，讓 Gateway 作為 OAuth2/OpenID Connect 的客戶端，統一處理認證流程，然後將 IdP 簽發的 Token 轉換為兩專案各自所需的認證憑證。
    *   在 Gateway 層實現**租戶 ID 映射與轉換**：將前端傳遞的通用租戶識別符，映射為專案 A 要求的獨立資料庫連線信息，或專案 B 要求的 `tenant_id` 請求參數。
*   **取捨**:
    *   **優點**:
        *   **高度解耦**: 兩專案後端保持獨立，業務邏輯改動互不影響，整合風險最低。
        *   **統一入口**: 為前端提供單一的 API 訪問點，簡化前端開發。
        *   **靈活的認證管理**: 能夠處理兩種不同的認證機制，或引入更標準化的認證流程。
        *   **解決多租戶核心問題**: Gateway 可作為租戶識別的翻譯官和分發器，無需大幅修改兩專案的租戶實現。
        *   **可擴展性與彈性**: Gateway 可獨立擴展，並易於增加額外功能 (如限流、日誌、監控)。
    *   **缺點**:
        *   **增加單點故障與延遲**: Gateway 可能成為系統的單點瓶頸或故障點，增加了一層網路呼叫。
        *   **額外的開發與維護成本**: 需要開發、部署和維護 Gateway 本身。
        *   **架構複雜度增加**: 引入新的組件，增加整體架構的複雜度。

### 選項二: 事件驅動架構 (Event-Driven Architecture) + 有限的 API 整合

*   **描述**: 透過事件匯流排 (如 RabbitMQ, Apache Kafka) 實現兩專案之間的非同步通訊，主要用於非即時的數據同步 (例如使用者或租戶基本信息)。對於需要即時互動的功能，仍透過各自的 API 進行。
*   **實施方式**:
    *   部署一個事件匯流排。
    *   專案 A 和專案 B 定義共享的數據事件 (例如 `UserCreated`, `TenantUpdated`)。
    *   當某專案中的特定數據發生變更時，發布相應事件到匯流排。
    *   另一個專案訂閱這些事件，並在收到事件時，執行相應的邏輯 (例如在自己的資料庫中創建或更新數據)。在此過程中，需要處理**租戶 ID 映射**和**數據轉換**邏輯。
    *   使用者介面仍然直接調用各自後端的 API，或透過一個輕量級的 API Gateway 進行路由。
*   **取捨**:
    *   **優點**:
        *   **高度解耦**: 服務間通過事件間接溝通，耦合度低。
        *   **異步處理**: 適合處理高吞吐量、非即時性的數據同步，提高系統響應性。
        *   **可擴展性**: 事件匯流排本身易於擴展。
    *   **缺點**:
        *   **資料最終一致性**: 數據同步存在延遲，無法保證即時一致性，需要業務邏輯容忍。
        *   **複雜性高**: 引入新的基礎設施和事件處理邏輯，錯誤追蹤和調試更複雜。
        *   **不適用於即時互動**: 無法解決即時性的 API 呼叫和認證共享問題。
        *   **租戶模型轉換挑戰依舊**: 事件處理器在接收事件時，仍需處理兩專案租戶模型的差異，進行複雜的數據映射。

**結論**: 鑑於兩專案多租戶模型和認證機制的根本性差異，**API 閘道模式 (選項一)** 是最推薦的初步整合方案。它能在不大幅修改現有系統核心邏輯的前提下，提供統一的對外介面，並處理認證與租戶轉換的複雜性，風險最低且彈性最大。事件驅動架構可作為後續數據同步的補充方案。

## 6. 建議的階段性里程碑 (MVP -> 擴充)

### 階段一：最小可行產品 (MVP) - API 閘道統一認證與核心路由

**目標**: 建立兩專案間的統一入口，解決認證與多租戶模型的核心差異，實現基本功能互通。

*   **1.1 API Gateway 選型與部署**:
    *   評估並選擇合適的 API Gateway 解決方案 (例如基於 FastAPI 自建輕量級 Gateway 或使用 Kong/Envoy)。
    *   完成 Gateway 的基礎部署與配置。
*   **1.2 統一認證層建立**:
    *   在 Gateway 中實現統一認證邏輯：處理使用者登入請求，並根據目標服務 (A 或 B) 轉換或轉發認證憑證 (Session Token ↔ JWT Token)。
    *   實現登出功能，確保兩系統登入狀態同步清除。
*   **1.3 租戶識別映射與路由**:
    *   定義一套標準化的租戶 ID 格式。
    *   在 Gateway 中實現租戶 ID 映射服務，將標準租戶 ID 轉換為專案 A 的資料庫連線資訊或專案 B 的 `tenant_id` 請求參數。
    *   配置 Gateway 路由規則，根據請求路徑或 Header 將請求精確導向專案 A 或專案 B 的後端服務。
*   **1.4 專案 A 容器化**:
    *   為專案 A 創建 Dockerfile 和 Docker Compose 配置，使其能夠在容器化環境中運行。
    *   更新專案 A 的資料庫初始化與遷移流程，使其能在容器啟動時自動執行。
*   **1.5 核心功能驗證**:
    *   選擇一個簡單、跨專案的基本功能 (例如：使用者基本資訊查詢、或一個簡單的內容列表)，讓前端透過 Gateway 同時調用兩專案的 API 並顯示結果。
*   **產出**: 可運行的 API Gateway 服務；兩專案後端可透過 Gateway 進行基本認證與功能調用；專案 A 容器化方案；一份租戶 ID 映射與認證轉換規則文檔。

### 階段二：核心業務功能擴充與數據同步

**目標**: 擴展更多業務功能的整合，並處理關鍵業務數據的非即時同步。

*   **2.1 擴充 API 路由與授權策略**:
    *   將更多兩專案的核心業務 API 透過 Gateway 暴露，並配置詳細的路由規則。
    *   完善 Gateway 上的授權策略 (例如基於角色權限)，確保使用者只能存取其有權限的資源。
*   **2.2 共享使用者與租戶資料同步 (非即時)**:
    *   引入事件匯流排 (如 RabbitMQ 或輕量級 Kafka)，用於處理非即時的數據同步。
    *   設計並實現使用者和租戶信息的非即時同步機制：
        *   當專案 A 或 B 中使用者/租戶信息發生變更時，觸發事件並由另一方消費事件進行數據更新。
        *   在此同步過程中，需處理**租戶模型差異下的數據映射**和**數據轉換**邏輯。
        *   建立數據衝突解決策略。
*   **2.3 統一錯誤處理與日誌**:
    *   定義統一的 API 錯誤響應格式。
    *   將 Gateway 和兩專案的日誌收集到中心化日誌系統 (如 ELK Stack 或 Grafana Loki)，便於監控與問題排查。
*   **2.4 性能與穩定性測試**:
    *   對整合後的系統進行負載測試和壓力測試，評估 Gateway 和兩專案的性能瓶頸。
    *   根據測試結果進行系統調優。
*   **產出**: 更多業務功能 API 透過 Gateway 暴露；核心使用者/租戶數據的非即時同步機制；統一的錯誤處理和日誌規範；性能報告與調優建議。

### 階段三：性能優化、穩定性與進階功能探索

**目標**: 進一步提升整合系統的性能和穩定性，並探索更深層次的業務與技術整合。

*   **3.1 高可用與災難恢復**:
    *   實施 API Gateway 和兩專案後端服務的高可用性部署 (例如多實例、負載平衡)。
    *   設計並測試災難恢復策略，確保系統在部分故障時仍能提供服務。
*   **3.2 前端體驗統一 (可選)**:
    *   若業務需求強烈，考慮採用微前端 (Micro-frontend) 架構，或者在其中一個專案的前端中嵌入另一個專案的功能頁面，提供更一致的使用者體驗。
*   **3.3 LLM 服務抽象與協調 (可選)**:
    *   在 Gateway 層或獨立的服務中抽象 LLM 呼叫邏輯，實現統一的模型選擇、配額管理和響應格式處理，提升 LLM 資源的利用效率和管理便利性。
*   **3.4 共享知識庫探索 (可選)**:
    *   研究如何讓專案 A 的知識庫內容與專案 B 的 `pgvector` RAG 能力結合。這可能涉及將 A 的知識庫數據進行轉換，並同步到專案 B 的 PostgreSQL 數據庫中。
*   **產出**: 具備高可用和災難恢復能力的整合系統；(可選) 統一或部分統一的前端體驗；(可選) LLM 服務協調機制；(可選) 共享知識庫方案。
